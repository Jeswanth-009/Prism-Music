# Prism Music: application audit and prioritized roadmap

Audit date: 6 October 2026. Workspace: C:\Prism Music.

## 1. Executive assessment

Prism is a promising Android music-player alpha, not yet a dependable public release. The application has real working components: playback, Android media notification integration, local library storage, provider fallbacks, lyric matching, reusable UI components and an automated test suite. It is not merely a mockup.

However, attractive screenshots currently overstate product completeness. Several visible features are misleading, incomplete or incorrectly wired. The highest priorities are reliable playback state, correct audio identity, trustworthy charts, durable library changes and safe backup handling. A further visual redesign without those repairs would not resolve the problems users are experiencing.

My critical UI assessment: the current dark player is the strongest screen. The Home page is artwork-heavy but does not make discovery especially efficient. Navigation, collection pages, actions, loading states and light-theme/accessibility handling do not yet feel like one finished product. The problem is not simply the color palette. Information hierarchy, density, consistent controls, truthful content and predictable behavior need work.

This is an audit, not an implementation. No application code was changed, no APK was installed or rebuilt, and nothing was pushed to GitHub.

### What the phone test does and does not prove

The installed release did not crash in this particular playback/background/pause test, and a media notification was posted. It does NOT establish that the previously reported crash is fixed for every source or device.

Retained Android process-exit records included low-memory terminations and OEM screen-off killer force-stops. No retained Prism Java/native crash was found in the inspected evidence. These exits are relevant to background reliability, but are not proof of the cause of the earlier song-start crash. A reproducible failure plus the corresponding fatal stack trace is still needed before declaring that historical issue solved.

The tested installed APK is newer than the local pubspec. Its exact binary/source equivalence was not established. Source findings below apply to the checked-out revision; phone observations apply to the installed application.

### Priority definitions

- **High:** release-blocking reliability, data loss, wrong/misrepresented content, or significant conditional security exposure.
- **Medium:** substantial usability, correctness, resilience, accessibility or maintainability issues; schedule immediately after release blockers.
- **Low:** polish, cleanup or documentation improvements with smaller direct impact.

“Source-confirmed” means the implementation contains the described defect. It does not mean every downstream symptom has been reproduced on the phone.

## 3. High-priority functional fixes

### F01 — Playback startup waits for the entire playback lifetime

**Category:** audio / state management. **Evidence:** source-confirmed.

`lib/core/services/audio_player_service.dart:291` awaits just_audio's `play()`. `lib/presentation/blocs/player/player_bloc.dart:514` awaits that wrapper before committing stream metadata, resetting position, recording history, marking reliability success and notifying queue changes.

The locally installed just_audio 0.10.6 documentation explicitly says that this future completes when playback completes, pauses or stops—not when audio has started. Independent engine streams can make the song audible while the play handler remains suspended.

**Impact:** delayed/missing history and recommendation bookkeeping; pause can release an old handler that then emits playing/reset position; changing songs can discard bookkeeping through the generation guard.

**Required fix:** treat start playback and lifetime completion as separate operations. Establish authoritative state through engine events, handle the play future's errors, and commit history exactly once after a defined successful-start/listening threshold. Do not simply discard an unhandled future.

**Acceptance:** use a fake whose play future remains pending until pause/completion. Verify play state and history update before completion; pause must remain paused; skip must not replay stale state.

### F02 — Stop/pause and asynchronous source resolution can conflict

**Category:** audio concurrency. **Evidence:** source-derived risk.

PlayerBloc generation checks surround asynchronous source setup, but Stop does not invalidate the active playback generation. Default concurrent event processing allows an outstanding resolution/source setup to finish after a newer user command. Generation checks do not cancel the underlying native operation.

**Required fix:** one serialized playback-command controller, cancellation/invalidation for stop and replacement, request-scoped resolver cancellation, and an explicit desired playback state.

**Acceptance:** play then immediately stop; rapidly choose A/B/C; pause while resolving; reconnect after failure. Only the last intended track and state may win.

### F03 — Mid-stream native errors are not comprehensively forwarded

**Category:** crash/recovery. **Evidence:** source-confirmed integration gap.

AudioPlayerService subscribes to player state/processing streams but does not connect the underlying player's native error stream to its wrapper error stream. Catching source setup errors is not sufficient for decoder/network failures that happen later.

**Required fix:** retain/cancel native subscriptions, translate native errors into structured failures, guard asynchronous initialization, and provide bounded retry or an explicit recoverable error state.

**Acceptance:** expired URL, mid-track disconnect, invalid codec, 403 and corrupt file must not close the app or leave an infinite spinner.

### F04 — A Jio search can play the wrong recording

**Category:** provider correctness. **Evidence:** source-confirmed.

`lib/data/datasources/remote/jiosaavn/jiosaavn_datasource.dart:86` selects `results[0]` from a search. There is no robust title/artist/duration/version confidence gate before substituting that recording for a selected YouTube track.

**Impact:** the UI can show one recording's metadata while playing a remix, cover, live version or different artist.

**Required fix:** prefer verified provider IDs; otherwise score candidates with Unicode-aware title, artist, duration and version matching. Reject ambiguous candidates and try another source rather than silently changing the song.

**Acceptance:** fixtures for similarly named songs, instrumental/live/remix versions, multiple artists and regional scripts; metadata and audio identity must remain consistent.

### F05 — Named charts are not actual ranked charts

**Category:** content trust. **Evidence:** source-confirmed.

`lib/core/services/chart_service.dart:112` and the YouTube chart method explicitly disable chart scraping and substitute search queries. Results are capped at about 25 and displayed under names such as Hot 100/Global 200 with apparent ranks.

**Required fix:** preserve chart navigation, but either implement a reliable ranked source with provenance, country and chart date, or relabel these as search-based discovery mixes. Do not label search position as official rank.

**Acceptance:** provider fixtures establish rank/order/date; fallback UI explicitly says it is a discovery mix. Provider failure is distinguishable from an empty chart.

### F06 — Library loading can remain stuck on a partial failure

**Category:** persistence / state. **Evidence:** source-confirmed.

`lib/presentation/blocs/library/library_bloc.dart:47` nests result folds. Some nested failure branches do not emit a terminal state. A playlists/history/recent/download load failure can leave the library loading or hide usable partial data.

**Required fix:** aggregate independent results, expose partial-success data and per-section errors, and guarantee a terminal state for every branch.

**Acceptance:** separately fail every repository call; usable sections remain available and failed sections offer retry.

### F07 — Imported playlists can report success without durable metadata

**Category:** data integrity. **Evidence:** source-confirmed.

`lib/presentation/blocs/library/library_bloc.dart:274`: new imports create a basic playlist and save songs individually. Artwork/author/source IDs are added to the returned in-memory copy, not durably saved with that complete object. Refresh writes only songs and explicitly ignores write failure; create failure can still return a playlist as “new.”

**Impact:** restart loses import identity/metadata; repeated imports can duplicate; success feedback can be false; partial playlists remain after interrupted import.

**Required fix:** transactional bulk upsert of complete playlist metadata plus songs; preserve source IDs; propagate persistence failures; return a clear import summary.

**Acceptance:** restart after import, reimport same URL, storage failure halfway through, interrupted import and refresh with changed name/artwork.

### F08 — Queue edits and shuffle do not maintain a coherent identity/index

**Category:** playback correctness. **Evidence:** source-confirmed state inconsistencies; exact symptoms need regression tests.

The queue and originalQueue snapshots are not consistently updated across shuffle/add/remove/reorder. Shuffle changes order without consistently preserving the current song's index. Toggling shuffle off can restore an obsolete original queue.

**Required fix:** use stable queue-item identity, preserve current item when shuffling, define original ordering semantics, bounds-check edits and reconcile native notification state on every change.

**Acceptance:** delete before/current/final item, edit while shuffled, unshuffle after deletion/addition, reorder current item and duplicate-track cases.

### F09 — Search filters can immediately submit the old filter

**Category:** search usability. **Evidence:** source-confirmed.

`lib/presentation/pages/search_page.dart:73` dispatches UpdateFilterEvent, then calls _onSearch, which reads the current BLoC state. The update is asynchronous, so the second query can carry the old filter.

**Required fix:** submit the selected filter explicitly in the new query, or let one BLoC event atomically update filter and execute search. Also invalidate stale requests on clear.

**Acceptance:** rapidly switch Songs → Artists → Albums with a nonempty query. Both selected chip and results must reflect the last selection.

### F10 — Album browse IDs are routed to a playlist API

**Category:** navigation / catalog. **Evidence:** source-confirmed.

`lib/presentation/pages/album_page.dart:48` passes album.id to getAlbumDetails. `lib/data/repositories/music_repository_impl.dart:305` treats it as a YouTube playlist ID. YouTube Music album browse IDs and playlist IDs are distinct; the model has a separate youtubePlaylistId field.

**Required fix:** implement a real album-details path, or pass the verified playable album playlist ID while preserving album metadata.

**Acceptance:** browse/search multiple albums and compare complete ordered tracks and artist metadata.

### F11 — Regional-script lyric matching is damaged by ASCII normalization

**Category:** lyrics / internationalization. **Evidence:** source-confirmed.

`lib/core/utils/lyrics_matching.dart:130` removes everything outside a-z, digits and whitespace. Titles/artists written in Tamil, Telugu, Hindi, Korean and other scripts can collapse into empty/incorrect matching tokens.

**Required fix:** Unicode-aware normalization and tokenization, script-preserving comparisons, and tests for multilingual titles and mixed-script names.

**Acceptance:** original-script and transliterated fixtures; unrelated empty-normalized titles must never be treated as matches.

### F12 — Release signing is allowed to fall back to a public debug key

**Category:** release integrity. **Evidence:** source-confirmed.

`android/app/build.gradle.kts:85` permits release signing with the debug config. The debug configuration uses the tracked android/app/debug.keystore. Both release workflows permit missing production signing credentials.

**Required fix:** fail release publication when production signing is unavailable; use a stable protected release key; document certificate fingerprint and migration. Do not assume previously distributed APKs can update across a certificate change.

**Acceptance:** a credential-less release must fail before publication; verify APK certificate and update installation without losing user data. See security S02.

## 6. Security and privacy backlog

No remotely exploitable critical vulnerability was demonstrated. The conditional findings below must not be advertised as proven remote compromise.

| ID / priority | Evidence and threat | Required remediation and verification |
|---|---|---|
| S01 — High, conditional local threat | LocalBackupService restores mutable shared-storage JSON including download.localPath; LocalDataSource later deletes File(path) without ownership validation (`local_datasource.dart:590`). A party able to alter a restored backup could point a download entry at another file the app can delete. This is constrained by Android filesystem permissions and requires a malicious local/imported backup, not simply an internet request. | Validate backup schema and path provenance; canonicalize and restrict deletions to app-owned download roots; reject symlink/path escapes; treat restored paths as untrusted and require reconciliation. Test crafted backups without touching real user files. |
| S02 — High release-integrity concern | Production publication accepts a tracked public debug signing key. Anyone possessing that same key can sign an APK with the same certificate; risk still requires the user to install a malicious APK. | Fail closed for public releases, protect a stable release key, verify certificate fingerprint, explain migration of existing installs and preserve library export. |
| S03 — Medium | Automatic shared-storage JSON contains listening/library/search information and file paths without encryption or clear consent/status. “Local” does not mean inaccessible to every other app/user with storage access. | Private storage by default; explicit export opt-in; describe location/data/risks; offer encrypted portable exports and delete/disable controls. |
| S04 — Medium | Manifest globally permits cleartext traffic (`AndroidManifest.xml:43`). | Require HTTPS for remote providers/streams where supported; use narrow loopback exceptions if the audio proxy needs them. Test headers/proxy playback before tightening policy. |
| S05 — Medium | Release logging includes search queries, stream URLs and response headers; signed URLs can be exposed through logs/diagnostic sharing. | Disable verbose release network logging; redact tokens, signed URL query strings and personal queries; make diagnostic export explicit and minimal. |
| S06 — Medium | Backup reads are unbounded JSON with weak version/type/count validation. Provider playlists/imports can also load large collections into memory. | Enforce byte/item/depth limits, timeouts, schema validation and paginated processing. Reject corrupt data without overwriting a healthy library. |
| S07 — Medium | Download filenames include provider IDs without a canonical allowlist; restored/provider paths and returned stream URLs are not centrally validated. | Generate internal UUID filenames, canonicalize paths, validate URI schemes/host policy and reject path separators/traversal. Ordinary provider IDs were not shown to exploit this in the test. |
| S08 — Medium, latent | Unused StreamProxyService binds all IPv4 interfaces and proxies a caller-supplied target URL with permissive CORS. It was not found active in the current application path. | Remove it or constrain to loopback with authenticated/allowlisted targets before enabling it. Do not call this a currently exposed network service. |
| S09 — Medium | Spotify shortened-link recognition uses a substring-style hostname check, potentially accepting an attacker-controlled lookalike host and following redirects. | Exact host/allowed subdomain validation; validate redirect targets and schemes; avoid private/local-network destinations in user URL fetching. |
| S10 — Medium | Last.fm session key is stored in a plain Hive box; the integration currently has placeholder API credentials. | Keep the feature disabled until configured; store tokens in OS-backed secure storage, redact logs and support revocation/logout. Do not attempt to hide a production API secret merely by embedding it in Dart. |
| S11 — Medium | Startup requests permissions beyond the immediate streaming need; manifest includes broad legacy/all-files/media-image capabilities. | Request just in time and minimize scope; app-private downloads should not require blanket all-files access. Explain optional notification/battery guidance without blocking core playback. |
| S12 — Medium | CI actions/Flutter channel are not fully immutable; publication permissions are broad and artifacts lack comprehensive provenance/SBOM checks. | Pin toolchain/action revisions, limit write permissions per job, scan dependencies and produce hashes, certificate checks and provenance. |
| S13 — Low | Privacy/backup marketing is broader than the actual behavior. Third-party metadata, lyrics, streaming and optional scrobbling necessarily make external requests. | Publish a precise data-flow/privacy explanation and qualify reinstall-survival guarantees by storage/permissions. |

Not findings: Jio's protocol DES key is not a leaked app account secret. Last.fm placeholder strings are not leaked live credentials. AudioService's normal exported media components are not by themselves proof of a vulnerability. No production keystore leakage was demonstrated. No owned server/backend was found, so server SQL/JWT/authentication findings would be invented rather than evidence-based.

### Shared design system work

1. Establish one spacing/type/radius system and apply it across every collection route.
2. Standardize song row anatomy: artwork, title, artist/version, current-playing state, download state and visible overflow action.
3. Create a common collection header with real content, Play/Shuffle and consistent metadata.
4. Make sheets scrollable at large text and with the keyboard visible.
5. Test both themes across selected/unselected/disabled/error states; do not infer contrast from HSL lightness alone.
6. Add semantic selected states, focus/keyboard support, practical touch targets and reduced-motion behavior.
7. Remove duplicate prominent content rather than filling the Home screen with repeated covers.
8. Define global playback error UX and keep access to now playing while browsing detail pages.
9. Profile blur/shimmer/palette effects on the actual low-end phone; reduce effects when they cost responsiveness.
10. Add adaptive tablet layouts and large-text layouts before claiming responsive design.

The redesign should improve task completion, not just colors: find a song, confirm it is the correct recording, play it, navigate freely, save it reliably and recover from failure.

## 8. Backend, API and data-flow assessment

There is no owned backend implementation in this repository that can be assessed as a deployed server. Most work happens on-device.

| Integration | Role | Main limitation |
|---|---|---|
| YouTube Music / youtube_explode | Search, metadata, playlists and audio resolution | Unofficial response contracts, parsing changes, provider blocks and multiple overlapping fallback paths |
| JioSaavn and third-party metadata endpoint | Metadata/source matching and playback fallback | First-match identity substitution; endpoint availability; quality setting mismatch |
| Piped / Invidious | Alternative stream extraction | Hardcoded public instances; health/concurrency issues; pagination and truthful codec classification |
| Spotify embed/import | Public playlist metadata converted to other playable sources | Scraped HTML contracts, limited pagination, ambiguous conversions and silent unmatched tracks |
| LRCLIB | Plain and synchronized lyrics | Matching/normalization/version handling; unavailable content and outage distinction |
| Last.fm | Optional authentication/scrobbling/profile features | Placeholder credentials and incomplete production-ready integration |
| Hive / filesystem | Library, history, settings, downloads and backup | Migrations, transactions, ownership validation and durability |

Recommended boundary: a typed provider interface with metadata identity, source capability, cancellation, deadlines, pagination, structured failures and health reporting. Keep metadata selection separate from audio selection. Store provenance and match confidence rather than pretending every converted item is identical.

Do not introduce a server merely to make the diagram look professional. A proxy/backend brings operating costs, abuse control, privacy and legal obligations. Decide whether one is necessary only after measuring provider reliability.

Provider terms, copyright/licensing and redistribution/download rights require a separate qualified review. This code audit does not establish permission to stream/download every provider's content.

## 9. Lyrics: where they come from and what remains

Lyrics currently come from LRCLIB through `lyrics_datasource.dart`, not from Spotify and not an owned Prism lyrics database. The application tries an exact lookup and scored search, and caches results locally. It supports plain/synchronized lyrics and displays provider attribution.

Existing strengths: request identity guards, duration-aware matching attempts, multiple LRC timestamps and forced refresh.

Remaining work:

- High: preserve non-Latin scripts in matching (F11).
- Medium: strengthen artist confidence; the score threshold can accept an exact title with a weak/wrong artist.
- Medium: include recording duration/version/provider record in cache identity; stripping live/remaster/version indicators can select incorrectly timed lyrics.
- Medium: use artist-specific normalization for artist queries, distinguish outage from unavailable lyrics, and honor cache freshness.
- Medium: support LRC offset metadata and user sync correction; keep playback controls visible.
- Low: allow tap-to-seek and a clear manual-scroll/follow-current-line toggle.

## 12. Test and release plan

### Why 132 passing tests are insufficient

The suite is useful, but only 28.80% of instrumented executable lines were hit. This excludes native verification and says little about provider/network failures. Fast fakes returning immediately from play do not model just_audio's lifetime future.

The integration flow does not establish a real Android notification assertion merely by checking BLoC song metadata. Simulated Dart lifecycle calls do not replace screen-off/Home-button tests. Golden baselines cover selected components/screens, not the entire application across phone sizes, themes and text scales.

### Required gates

| Priority | Tests |

## 13. APK size and platform packaging

A new exact APK-size breakdown was not measured in this audit; the previously reported 60+ MB is not independently confirmed here.

The workflows already distinguish ARM phone builds from an x86_64 emulator build. That is a useful improvement. Keep one simple phone download prominent for nontechnical users; make emulator artifacts explicitly secondary.

For further optimization:

1. Analyze the actual release APK by native library/ABI, Dart snapshot, assets and resources.
2. Keep release shrinking/resource shrinking and verify notification resources survive; a notification icon keep resource is already present.
3. Remove unused dependencies/assets only after confirming references.
4. Consider an optional arm64-only download alongside the inclusive ARM phone APK, not as a mandatory technical choice.
5. Do not remove needed codecs/native services blindly to hit an arbitrary size.
6. Publish measured compressed download size and installed size separately.

Universal multi-ABI packaging duplicates native binaries by design. There is a real size/compatibility tradeoff, not a magic setting that removes it with no cost.

## 14. Documentation and open-source readiness

Strengths: public code, separable service/repository concepts, reusable components, existing CI/tests, a landing page, release automation and an identifiable product purpose.

Weaknesses: incomplete features presented as complete, provider fragility, release trust/signing, stale architectural documentation, limited contributor-grade reproducibility and insufficient real-device release validation.

Before promoting the project broadly:

- Clearly label alpha status and supported platform/device requirements.
- Publish truthful feature support, provider limitations and known issues.
- Add reproducible toolchain instructions and a small architecture/data-flow guide.
- Provide a bug template requesting version, provider/track, network, steps and redacted logs.

- Make privacy/backup behavior understandable and opt-in where appropriate.
- Document contribution/testing/release ownership and dependency/license attribution.
- Separate verified phone release assets from emulator assets.

The project can become a good open-source application, but reliability and honesty will earn more trust than another dramatic cosmetic rewrite.

## 15. Recommended execution order

### Stage A — release blockers

F01–F04 playback/identity; F06–F08 library/queue durability; S01 path-safe restore; F12/S02 signing. Add regression tests as each is fixed. Capture the earlier crash if it returns.

**Exit:** no stale play commands, no silently wrong recording, durable writes, safe restore and signed/version-verified release artifact.

### Stage B — core usability and truthful content

F05/F09/F10/F11 charts/search/albums/lyrics; repair download workflows and player recovery; remove/disable dead effects/login/layout options until implemented.

**Exit:** users can find the right song, open a collection, play/download/save it, restart and recover from an outage without misleading feedback.

### Stage C — cohesive visual redesign

Apply the shared component system and page-by-page changes above. Validate Home and Player first, then collections/search/settings. Keep actual working data and actions throughout.

**Exit:** consistent route anatomy and player access; no content obstruction; usable light/dark, large text and narrow phones; every visible action is meaningful.

### Stage D — hardening and growth

Provider contracts/health, profiling, contributor docs, localization, recommendation controls and carefully chosen future features.

Do not start all stages simultaneously. Publish only when the relevant acceptance gates pass, not just when code compiles.
